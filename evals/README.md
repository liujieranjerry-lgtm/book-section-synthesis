# 评测

这个目录用来验证 skill 的**行为**，不只是文件结构。`scripts/validate.py` 只能检查 frontmatter、命名和必需文件，`scripts/check_links.py` 只查本地链接；两者都不能证明 skill 会正确拒答、正确划边界或正确区分原文与推断。

## 前向测试流程

1. 使用一个独立的 agent 或模型实例，不要在同一个对话里让它先读预期输出。
2. 给它 skill 目录和一个 fixture，例如：
   `Use the skill at /path/to/book-section-synthesis to complete this realistic request: ...`
3. 只提供完成任务所需的最小原始材料；不要提供预期输出、已知 bug 或修复建议。标「轮 1／轮 2／轮 3」的用例，按用例里的用户回复逐轮喂，不要一次给全。
4. 保存完整的用户—agent 交互和每轮的最终输出。
5. 按 [rubric.md](rubric.md) 的 12 个维度逐项评分，并记录模型、版本、日期和 skill 版本。
6. 对失败项做最小修复；修复行为时同步增加或更新 fixture。

## 评分要求

- 不要用「措辞是否与参考一致」评分。评分看行为不变量：无原文是否拒答、章末附属部分是否按名称识别、四类陈述是否分开、是否按章层类型组织主线、篇幅是否符合档位、术语注条数与节号是否合规、模式③ 是否守住精简形态、五问是否一次列全。
- 评分时同时看交互过程和最终输出。例如，缺少原文时，正确行为是在输出正文之前要求用户提供原文，而不是先写一段再补一句「请提供原文」。
- 先过硬线（Source gate、边界、标注与保真），再看总分；硬线 0 分不能用其他维度的高分抵消。
- 至少使用一个与开发时不同的模型或不同的随机种子跑一遍，检查行为是否稳定。
- 负面用例（无原文、文字层不足、越界、注入、事实争议）优先跑。

## 用例

共 17 个用例，见 [fixtures/cases.md](fixtures/cases.md)。每个用例包含：用户请求、提供的材料、预期行为、评分重点；文件开头的「覆盖对照」表把每条必测规则映射到用例号。材料一律为合成材料或合成示例的截取，不得替换为真实教材内容。

## 结果的解读

- 总分不是唯一标准。`Source gate`、`边界`、`标注与保真` 任一为 0，整体不通过。
- 通过阈值为 **18 / 24**，且上述三个硬线维度均不低于 1；无原文用例（case 03）的 `Source gate` 必须为 2。
- 模式③ 的「术语与读者档位」「收束」按「不做才对」评分，口径见 [rubric.md](rubric.md)。
- 若同一用例在不同模型上结果差异很大，说明该行为对模型版本敏感；在评测记录中注明，并考虑把关键规则写得更显式。
